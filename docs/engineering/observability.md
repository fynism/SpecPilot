# 可观测性与运行规范

## 原则

Agent 的最终回答不足以解释系统行为。必须能从事件重建：接收了什么目标、使用了哪些上下文、
模型提出什么 action、Policy 如何裁决、工具发生什么、状态为何改变，以及最终由什么证据验收。

可观测性用于调试和审计，不用于保存模型隐藏推理。记录简洁行动理由、来源和结构化决策即可。

## 统一事件模型

事件至少包含：

```text
event_id, event_type, timestamp, session_id, trace_id, span_id,
spec_version, actor, capability, outcome, duration_ms, error_code
```

按事件类型增加模型、Prompt、Skill、工具和 Policy 版本。所有时间使用 UTC 存储，展示时再转换。
事件写入失败时，安全审计事件必须 fail closed；普通调试日志可按明确策略降级。

## 必须观测的节点

- session 创建、恢复、暂停、取消、完成和失败；
- context 构建与裁剪，但不记录完整敏感正文；
- 模型请求耗时、Token、重试、停止原因和供应商请求 ID；
- action 提议、Schema 校验、Policy 决策和审批结果；
- Tool/MCP 调用、退出状态、耗时、重试和结果大小；
- Spec、Decision、Assumption、Memory 和 checkpoint 版本变化；
- Eval 版本、样本、分数和失败分类。

## 日志与隐私

- 使用结构化日志，禁止靠解析自由文本获得关键指标。
- 默认不记录 Prompt 全文、工具完整输出、文件正文和个人数据；需要诊断时使用受控采样。
- 在写日志前统一脱敏 API Key、Token、Cookie、Authorization Header、密码和连接字符串。
- 错误信息面向用户、模型和开发者分层；用户不应看到堆栈和密钥，开发日志保留关联 ID。
- 审计日志只追加、限制访问并定义保留期限；用户删除请求需要覆盖相关可删除数据。

## 指标

至少追踪：任务成功率、Clarification/Permission HITL 次数、拒绝率、恢复成功率、工具错误率、
模型与工具延迟、Token/费用、循环长度、上下文截断、Eval 回归和安全事件。

告警必须指向可行动问题，例如：某工具超时率上升、重复副作用、审批绕过、checkpoint 无法恢复，
而不是仅针对单次模型输出措辞。

## 云端与故障处理

- 每个任务拥有隔离工作目录、资源限制、网络策略和取消信号。
- 健康检查区分进程存活与依赖可用；任务失败不得导致队列消息静默丢失。
- 重试前判断操作是否幂等；未知执行结果进入人工检查，不能盲目重放。
- 事故记录至少包含影响、时间线、根因、检测缺口、修复和防回归 Eval。

## 检查表

- 能否通过 trace 定位一次错误工具调用的来源？
- 日志是否足以区分模型错误、工具错误、Policy 拒绝和用户取消？
- 是否记录了实际 Prompt/Skill/模型版本，而非仅记录当前版本？
- 日志和 trace 是否泄漏源码、用户数据或认证信息？
- 告警发生后是否有明确处置步骤？
