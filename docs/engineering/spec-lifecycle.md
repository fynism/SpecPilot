# Spec 与需求澄清规范

## Spec 的定位

Spec 说明产品要解决什么、交付边界是什么，以及什么结果算满足需求；Plan 说明在当前仓库中如何实现。Markdown 是结构化 Spec 的可读视图，不能作为独立事实源。

当前精简 Spec v2 只包含五类内容：

- `goal`：单一产品目标与期望结果；
- `boundaries`：纳入范围、排除范围和明确约束；
- `requirements`：可验证的产品行为，每条需求直接包含 `acceptance_examples`；
- `decisions`：用户明确确认的产品选择及其理由和来源；
- `evidence`：用户回答、仓库材料或测试等结论来源，由实体 ID 引用。

未确定的低影响细节保持未指定，不写成假设或默认值。技术实现决策属于 Plan；仓库现状是 Evidence 或约束，不应伪装成用户产品决策。

未决问题只保存在 Clarification Plan 中，不复制成 Spec 实体。主题和问题记录未知点、依赖、回答及复核状态；用户提交的答案由宿主生成不可改写的 Evidence。Spec 中只记录已确认的产品事实和决策。

实体使用稳定 ID。语义变更保留旧版本与变更理由；过时实体标记停用或由新决策 supersede，不删除历史来掩盖变化。

## 澄清策略：持续追问关键问题

先理解目标，再查证据，最后问用户。遇到不确定性时：

1. 先从用户原话、仓库和已确认结论中查找答案；廉价可查证的问题不问用户。
2. 评估未决点对产品行为、范围、成本、风险和返工的影响，只优先问能改变结果的关键问题。
3. 若后续选择依赖一个前提，先问前提；独立问题只在每个问题都值得单独回答时合并。
4. 每轮发布 1–3 个问题，不为填满轮次而追加问题。问题简洁说明缘由，给出互斥选项、一个推荐及理由，并允许自由回答和补充条件。
5. 收到回答后保留原意和限定条件，检查答案引发的依赖和旧结论复核，再决定下一轮要问什么。

当核心行为、边界和验收示例已经足以供用户审阅时停止追问。发布空问题轮次，并说明可审阅，或指出具体缺少的需求/验收信息。用户可以继续补充，也可以随时结束澄清；结束后只总结已有结论和未决点。

推荐选项不等于用户决定。只有用户明确选择或确认的产品行为才能成为 `Decision`，且必须引用用户陈述或澄清 Evidence。不要猜测答案、补造默认值或把模型建议记录为事实。

## 就绪与批准

结构校验和完整性校验由代码执行。Spec 至少需要一个有效目标、一条有效需求，并且每条有效需求包含至少一个可验证示例。澄清计划仍有阻塞、待提交或待复核事项时，宿主不会将 Spec 设为待审阅。

空轮次本身不代表完成。只有宿主在问题轮次成功发布后，结合 Spec 与澄清状态计算 `ready_for_approval`。模型不能自行设置待审阅或已批准状态；用户批准是后续独立动作，也不代表实现完成或授予危险操作权限。

新提交或语义修改会撤回旧的待审阅/批准状态。实现发现新业务事实时回到澄清，不得由 Plan 静默修改 Spec。

## 验收与 Plan 衔接

- 每条关键需求写清可观察行为和验收示例；按需覆盖主路径、权限、失败和边界情况。
- 安全、性能、兼容性等约束写成可验证条件，不为套用 BDD 格式而拆出独立验收实体。
- 自动化测试或人工检查结果可作为 Evidence；测试通过不代表未覆盖的需求已验证。
- Plan 可提出技术风险和实现方案，但不能改写产品需求或用户决策。需求变化必须重新澄清并产生 Spec 新版本。
- 导出面向产品审阅，默认显示目标、边界、需求、验收示例和已确认决策；内部证据仅作为可追溯信息，不要求用户阅读完整事实源。

## 质量检查

- 是否表达清楚目标、范围边界和关键约束？
- 是否明确关键产品行为、异常情况和权限边界？
- 每条关键需求是否有可观察的验收示例？
- 决策是否由用户确认并能追溯到来源？
- 是否先调查了可从仓库回答的问题？
- 是否持续追问了会改变结果的关键未知点，并避免填充式问题？
- 是否把实现方式误写成产品需求，或把模型建议误写成用户决策？
