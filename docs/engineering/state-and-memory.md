# 状态、持久化与记忆规范

## 必须区分的状态

| 类型 | 内容 | 默认生命周期 |
| --- | --- | --- |
| Session State | 消息、当前行动、预算、暂停原因 | 单会话 |
| Spec State | 需求、决策、假设、验收和证据 | 单项目、版本化 |
| Project Memory | 架构惯例、术语、稳定项目事实 | 项目级，可修订 |
| User Memory | 用户长期偏好 | 跨项目，需明确控制 |
| Execution/Audit | 工具、审批、错误和状态事件 | 按保留策略 |

记忆不能替代 Spec：项目或用户记忆只能提供候选默认值和证据；涉及本次高影响需求时仍需确认。

## 记忆记录

每条长期记忆至少包含：稳定 ID、内容、类型、来源、创建/更新时间、作用域、置信度、有效期、
敏感等级和状态。推断必须标注为推断，不能伪装成用户陈述。

- 支持更正、撤销和删除；新记录不得静默覆盖冲突记录。
- 检索结果保留来源和相关性；注入上下文前按权限、作用域和有效期过滤。
- 不保存密钥、认证信息、原始私密内容或无关个人数据。
- 用户应能查看系统记住了什么，并控制跨项目记忆。

## Checkpoint

Checkpoint 必须足以恢复而不重复危险副作用，包括：

- session/spec 版本；
- 当前生命周期状态和待处理 action；
- 已完成工具调用及幂等键；
- 待审批/待澄清请求及其参数摘要；
- 模型、Prompt、Skill、工具和 Schema 版本；
- 已消耗的轮次、Token、费用和时间预算。

保存采用事务或“临时文件 + 原子替换”。恢复时校验 Schema 版本、校验和以及待执行动作是否仍
有效；不兼容时停止并要求迁移，不能猜测修复。

## 当前本地 Session MVP

当前实现以 worktree 为作用域，在 `.specpilot/sessions-v5/` 中保存多个本地 Session。一个 Session
快照原子包含消息、当前请求、生命周期状态和完整 Spec 版本历史；索引只记录已知 Session 与
上次活动项。不同 worktree 不自动共享状态。

恢复边界是完整 Agent Loop 轮次：进入 Loop 前持久化 `running`，Loop 正常返回后持久化
`waiting_for_user`。启动时遗留的 `running` 转为 `interrupted`，但不会自动执行任何待处理动作。
这是可恢复对话的最小实现，不满足工具执行中 checkpoint、并发写入、事件审计或长期记忆需求。

### Session v5 与澄清恢复

Session v5 同时保存精简 Spec v2 历史、`clarification_plan`、`context` 和 `token_usage`。
澄清总览原子包含主题、问题版本历史、轮次、答案修订、补充草稿与提交状态。
答案编辑立即写稳定快照，不直接改变 Spec。下一次显式需求处理运行为真实提交创建 Evidence；普通聊天不消费提交；
最终总结轮不做该写入。模型变更仍只在完整 Loop 返回后提交；异常或重启发现 running
时标记 interrupted。捕获到的澄清运行失败将待处理提交标记 retry；普通聊天失败不修改提交。
进程意外退出后无法从 v5 的 active_request 字符串可靠恢复轮次来源，因此保留提交原状态；
pending 和 retry 均可由用户显式重试，不自动重放模型或工具。

已提交补充说明也生成宿主证据。宿主证据的命名空间不允许模型创建或覆盖；普通工具只引用
已有 ID。新澄清提交使原先待批准／已批准的 Spec 进入 revised，再开始模型运行。
运行起点保存失败时撤回未保存的宿主证据，保持已装配服务的 Store 身份和稳定快照一致。

独立 `context` 状态保存模型摘要、已摘要消息前缀位置，以及压缩
原因、模型、策略版本、来源范围、时间和前后估算 Token。原始 `messages` 不裁剪，Spec
版本历史不变；恢复、切换 Session 后继续使用该 Session 的摘要。手动压缩在轮次间原子保存，
运行中压缩随完整轮次提交，轮次失败丢弃未提交摘要。

`token_usage` 保存累计及本次实际输入/输出、调用数、缺失用量
调用数、上次调用用量，以及历史是否未统计。生成响应的 API 用量在稳定磁盘快照上立即
单独保存，不提交中间工具协议或 Spec；完整轮次失败恢复时仍保留已发生的消耗。手动摘要
即使失败或没有压缩收益，也会保留它的实际消耗。计数 API 调用不计入生成消耗。

旧历史无法重建实际消耗时必须标记未知。
统计缺失不允许用估算补零。上下文计数只在当前进程内按请求摘要缓存，启动/恢复后显示
“待计数”，下一次模型操作重新计数。切换 Session 保持消耗独立；普通输入和手动压缩会
开始新的本次统计，累计值持续增加。压缩不改变总览及草稿；新版澄清的提示词和工具声明
必须同样用于压缩前后计数，发布轮次暂停前刷新上下文计数。

### 旧格式与回退

v5 使用新的 `.specpilot/sessions-v5/` 目录，并严格要求 Session Schema v5 和 Spec Schema v2。
旧 `.specpilot/sessions/` 文件保持原样，不自动迁移或读取；旧数据仍可由旧版本程序访问。
如需迁移，必须另行设计并验证显式迁移流程，不能通过推测补造产品决策、需求或验收信息。
回退旧版本时，其原目录和文件仍在；v5 期间产生的 Session 与 Spec 变化不会出现在旧程序中。

## 并发与一致性

- 状态更新使用单写者或乐观锁版本号，禁止后写覆盖先写。
- 事件应有单调序号；重复事件通过稳定事件 ID 去重。
- 工具副作用与状态提交无法原子化时，使用幂等键和可恢复操作日志。
- 并行 Agent 不能直接共享可变内存；通过显式消息和版本化 artifact 协作。

## Schema 演进

- 持久化 Schema 必须带版本号；破坏性变更须使用新目录或经过审查的显式迁移。
- 不得静默推测丢失字段；新旧格式的测试必须验证数据保留和拒绝行为。
- Migration 必须可重复运行并在失败后安全重试；执行前备份重要数据。

## 检查表

- 进程在任意工具调用前后中断，能否安全恢复？
- 同一响应或 webhook 重复到达是否会重复副作用？
- 这条“记忆”是谁说的、在哪个范围有效、何时过期？
- 用户修改偏好后，旧记忆是否仍会污染上下文？
- 数据保留和删除策略是否明确？
